SPA/MPA는 한페이지로 웹사이트를 구성하느냐, 여러 페이지로 구성하느냐인데, 좀 더 분명한 차이를 알 수 있는건 "페이지 이동을 어떻게 하느냐"이다. JS를 요청하고 받아와서 클라이언트(브라우저)단에서 dom을 변경해 이동한것처럼 구현을 하는지, 실제로 풀페이지 html을 받아와 dom 전체를 언로드하고 새로 렌더링하는지이다.
내가 계속 착각한게 SPA는 클라이언트에서 내비게이팅을 해야만 하니까 csr이라고 생각했고, MPA는 서버에서 HTML을 받아와서 내비게이팅하니까 ssr이라고 생각한 것이다.
내비게이션 방식의 문제를 렌더링 위치와 헷갈린 것이다.
또한, 리액트와 같은 SPA 라이브러리 등장 전 전통적으로 SSR + MPA가 같이 쓰이고, 리액트에선 CSR + SPA으로 사용되는 방식에 익숙한 것도 있다. PHP가 HTML만들어보내고(SSR), 링크 누르면 새로고침(MPA) 방식으로 처음 웹개발을 배웠던 지라 SSR + SPA이나 CSR + MPA 등 다른 조합은 잘 연상이 안된 탓도 있을 것이다.

Next.js는 과거 웹의 문제들을 여러 조합으로 해결한 하이브리드 프레임워크라고 할 수 있다.
1. 서버 -> 완성된 HTML 전송 (SSR) => SEO 유리 (순수 리액트(CSR)의 단점 해결)
2. 브라우저 -> HTML 바로 표시 => 빠른 로딩 (리액트의 단점 해결2)
3. 브라우저 -> JS 로드 후 기존 DOM에 이벤트 연결 (하이드레이션) 
   => 없으면: React가 서버 HTML 무시하고 createRoot().render()로 DOM 덮어씀
   => 있으면: hydrateRoot()로 기존 DOM 인수인계받아 이벤트만 연결
4. 이후 링크 클릭 -> JS가 라우팅 처리 (Client side navigation) => 새로고침 없음 (MPA 단점 해결)

응. “깜빡임 없는 페이지 전환 = Client Side Navigation 때문”이라고만 말하기는 어렵다고 보는 게 더 정확해.

이유는 Client Side Navigation은 필요조건에 가깝고, 충분조건은 아니기 때문이야.

예를 들어 React SPA도 Client Side Navigation을 사용하지만, 페이지 전환 시 로딩 상태를 어떻게 처리하느냐에 따라 충분히 깜빡일 수 있어.

if (isLoading) {
  return <Spinner />;
}

이런 식으로 구현하면 화면이 비었다가 다시 그려지는 느낌이 날 수 있지.

Next.js가 비교적 부드럽게 느껴지는 건 여러 요소가 함께 작용하기 때문이야.

1. Client Side Navigation
    * 브라우저 전체 새로고침을 하지 않는다.
    * document 자체를 교체하지 않는다.
2. RSC Payload 전송
    * 전체 HTML 대신 변경된 UI 정보만 가져온다.
3. Partial Rendering
    * 변경된 segment만 교체한다.
    * 공통 레이아웃은 유지된다.
4. Prefetch
    * 필요한 데이터를 미리 받아둔다.
    * 전환 대기 시간이 줄어든다.
5. React의 상태 유지
    * 레이아웃과 클라이언트 컴포넌트 상태를 유지할 수 있다.

그래서 네 글에서 확인한 범위 안에서는

Link 컴포넌트를 이용한 Client Side Navigation과 일부 DOM만 갱신하는 방식 덕분에 전체 페이지 깜빡임 없이 전환된다.

정도로 표현하는 게 적절해 보여.

반대로

Next.js가 깜빡이지 않는 이유는 Client Side Navigation 때문이다.

라고 단정하면, 다음 글에서 RSC나 segment 단위 렌더링을 다룰 때 “그럼 그건 왜 필요하지?“라는 의문이 생길 수 있어.

그래서 지금 글의 결론처럼

Link 내비게이션에서는 text/x-component를 받아 변경된 segment만 교체한다.

정도까지 말하는 것이 현재 실험 결과와도 잘 맞고, 과장도 없는 표현이라고 생각해.
